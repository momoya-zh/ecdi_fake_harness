# ECDI_fake_harness 协议 v2

> **这个文件的定位**：`core`（Go）与 `gui`（C++ / ECDI）之间**唯一的契约**。
> 它先于两侧任何一行实现存在——因为 GUI 可以只看它就能跑起来。
> 状态：**v2**（2026-10-14；v1 起草于 2026-10-03）。改这份文件 = 改协议版本号。
>
> ★ **v1 → v2 改了什么**（2026-10-14）：
> ① §3.3 新增 `kind:"reasoning"`（思维链取得**一等公民**位置，不再是「未知 kind」）；
> ② §5 新增不变量 **I8**（未知 `kind` 必须中性渲染 + 显式提示）；
> ③ §7 新增 `reasoning` 的渲染形态（**默认收起，点击展开，箭头翻转**；已结束文案变 `已完成`）；
> ④ §3.1 新增 `hello.context`（**上下文占用百分比的分母**——此前协议里没有任何容量字段）；
> ⑤ §3.5 新增 `block_end.tokens`（思维链标题的 token 副标）。
> ★ **为什么这需要升主版本**：新增 `kind` / 字段本身都是「只增」的（旧 GUI 按 I5 忽略，不崩不丢），
> 但 **I8 是一条新的义务**——它约束的是「遇到不认识的东西时**必须**怎么做」，
> 属于契约面的扩大，不是纯数据面的追加。按 §9 第 3 条（改语义 ⇒ 主版本 +1）从宽处置。

## 0. 为什么是「假」harness

`gui` 是**协议的渲染器**。协议定好之后，GUI 可以对着**手写/录制的 JSONL** 跑完整个界面，
既不需要 Go 核心，也不需要模型。于是：

- 界面与流式渲染能**在没有 agent 的情况下**被开发与度量；
- 同一份夹具可以**离线重放**，成为回归基线；
- 项目的第一个可交付物是**评估 ECDI 的数据**，而不是一个 agent。

这是 ECDI 里 `RecordingBackend` 那个套路的第二次使用。

## 1. 编码与分帧

### 1.1 仓库编码约定

| 文件类型 | 编码 | 行尾 | 理由 |
|---|---|---|---|
| 文本（`.md` / `.cpp` / `.h` / `.go` / `.py`） | UTF-8 **带 BOM** | CRLF | 中文被 MSVC 按 CP936 读会 C4819 + 乱码（ECDI 条 70 的教训）；**一条规则 + 一个例外**比记一堆特例便宜 |
| **`*.jsonl`** | UTF-8 **不带 BOM** | **LF** | BOM 会破坏流式 JSON 解析；LF 是 JSONL 工具链的预期 |
| **配置文件**（`.gitignore` / `CMakeLists.txt` / `go.mod` / `*.json`） | UTF-8 **不带 BOM** | 随该工具的预期 | 与 ECDI 同源的例外：清单 / listfile 类文件以**解析兼容性优先**，BOM 会惹麻烦 |

### 1.2 分帧

- **一行一个 JSON 对象，`\n`(LF) 结尾**，行内不得有裸换行。
- 两侧各自独立地按行读；**读到不完整的最后一行（EOF 截断）必须报错，不得静默丢弃**。
- 未知字段**必须忽略**（前向兼容）；未知 `t` 值**忽略并记录**（不得崩溃）。
- 流里不允许 pretty-print（一行就是一整条消息）。

## 2. 信封

每条消息都是：

```json
{ "t": "<类型>", "seq": 0, "ts": "2026-10-03T10:40:00.000Z" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `t` | ✅ | 类型判别符，见 §3 / §4 |
| `seq` | ✅ | **每方向独立、从 0 起、严格递增**。缺口 = 丢失，见 I4 |
| `ts` | core→gui 必填 | ISO-8601 UTC（毫秒）。**回放的节奏唯一来源**（§8） |

`seq` 与 `ts` 不是装饰：它们**就是**评估指标 ①③ 的量具（§10）。

## 3. core → gui 消息

### 3.1 `hello`

握手的**第一条**消息，`seq` 必须为 0。

```json
{"t":"hello","seq":0,"ts":"...","protocol":2,"core":"0.1.0","session":"s-0001","caps":["tools","ask"],"context":128000}
```

| 字段 | 说明 |
|---|---|
| `protocol` | 协议**主版本**。GUI 的版本较低时必须拒绝并显示错误（§9） |
| `core` | 核心版本，仅用于显示 |
| `session` | 会话 id；`--resume` 时回放同一 id |
| `caps` | 能力声明，GUI 据此决定是否显示对应交互 |
| `context` | ★ **v2 新增（可选）**：上下文窗口容量（**token 数**）。= 「上下文占用百分比」的**分母** |

★ **`context` 为什么必须存在（2026-10-14）**：用户要求显示「上下文已占用的百分比」。
**百分比必须有分母**——而 v1 的协议里**没有任何字段**给出容量（`usage` 只有 `turn`/`input`/`output`）
⇒ 此前那两根用量条只能拿 `max(input, output)` 当分母，即**拿输入跟输出比**，**无意义**。
- **可选**：core 不知道容量（或模型未声明）时**可以不发**。此时 GUI **必须**显示 `—`
  而**不得**猜测或按 0 处理（分母未知 ⇒ 百分比无定义）。
- **量纲**：token 数（与 `usage.input`/`output` 同量纲），**不是**字节/字符。
- ⬜ **未定**：是否允许**按轮覆盖**（同一会话切模型 ⇒ 容量变）。当前只认 `hello` 这一个来源；
  真需要时按 §9「只增不改」加可选 `usage.context`。

### 3.2 `state`

```json
{"t":"state","seq":1,"ts":"...","value":"running"}
```

| `value` | 含义 |
|---|---|
| `idle` | 空闲，可接受 `prompt` |
| `running` | 正在处理 |
| `waiting` | **阻塞在一个未回答的 `ask` 上**（I3） |
| `cancelled` | 因 `cancel` 而停止 |
| `error` | 致命错误，随后进程退出 |

### 3.3 `block_start`

转录块的开始。**每个 id 只能出现一次**（I1）。

```json
{"t":"block_start","seq":2,"ts":"...","id":"b2","kind":"assistant"}
{"t":"block_start","seq":3,"ts":"...","id":"b1","kind":"user","text":"帮我看看 README"}
{"t":"block_start","seq":4,"ts":"...","id":"b3","kind":"tool_call","name":"read_file","args":{"path":"docs/README.md"}}
```

| `kind` | 用途 | 附带字段 |
|---|---|---|
| `user` | 用户输入（**由 core 回显**，见 §8.3） | `text` |
| `assistant` | 模型输出（通常流式） | — |
| `reasoning` | ★ **思维链**（开源推理模型在回答前流式吐出的推理过程） | `text`（流式走 `delta`） |
| `tool_call` | 一次工具调用 | `name`、`args`（原样 JSON 对象） |
| `tool_result` | 对应的结果 | `for`（被引用块的 id） |
| `system` | 系统提示 / 分隔 | `text` |
| `error` | 错误 | `text` |

可选 `text`：块的**初始文本**。最终文本 = `block_start.text` + 该块所有 `delta.text` 顺序拼接。

★ **`reasoning` 为什么是一等公民（v2 新增，2026-10-14 用户定调）**：用**开源推理模型**
（DeepSeek-R1 / QwQ 一类）时，core 会在回答前**流式吐出思维链**。它不是「另一种 assistant
文本」——三处都不同：① **长**（常是回答的数倍）；② **流式**（逐 token，每个 `delta` 都可能
触发重绘）；③ **默认不渲染**（用户多数时候不想读，故**收起**）。这三条合起来是一个**独立的
负载形状**，也是评估指标 ①/④ 的直接来源。

★ **它的存在方式 = 正式的 `kind`，默认收起**（渲染形态见 §7）：
- **必须是一等公民**，不是「未知 `kind` 的兜底路径」——否则「未知 kind 要中性渲染」这条
  通用规则会把它和真正的未知值混为一谈，且渲染形态无处规定；
- **默认收起**（用户口径：「默认应当不渲染」）——收起是**渲染层**行为，**不影响协议**：
  core 照常把完整思维链流式发完，GUI 负责折叠显示。★ 这与「协议不该管渲染」一致：
  `reasoning` 在**传输层**与 `assistant` 无差别，差别只在 §7 的渲染映射。

> ⚠️ **向后兼容**：v1 的 GUI 不认识 `reasoning` ⇒ 按 I5 走「未知 `kind` 中性渲染」路径
> （可见气泡 + 显式提示）。**不崩、不丢内容**，只是不折叠。这正是 I5/I8 存在的意义。

### 3.4 `delta`

流式增量。同一块的多次 `delta` 按 `seq` 顺序拼接。

```json
{"t":"delta","seq":5,"ts":"...","id":"b2","text":"我先看"}
```

### 3.5 `block_end`

块的终结。**此后该块永不再变**（I6）。

```json
{"t":"block_end","seq":13,"ts":"...","id":"b2","ok":true,"summary":"共 3 段"}
{"t":"block_end","seq":20,"ts":"...","id":"b8","ok":false,"summary":"2 项失败"}
{"t":"block_end","seq":41,"ts":"...","id":"b9","ok":true,"tokens":1843}
```

| 字段 | 说明 |
|---|---|
| `ok` | 该块是否成功 |
| `summary` | 可选短摘要（工具卡标题用） |
| `tokens` | ★ **v2 新增（可选）**：该块的 token 数。**`reasoning` 块**用它做标题副标（§7） |

★ **为什么 `tokens` 放在 `block_end` 而不是 `block_start`**：token 数**只有内容产完才知道**
——`block_start` 时正文还没流过来。放 `block_start` 会逼 core 要么预知（不可能）、
要么先发后改（违反 I6「`block_end` 之后只读」的精神）。
★ **可选**：core 不算 token（或用的分词器不报）时可以**不发**。此时 GUI **不显示**该副标，
**不得**用字符数冒充实测 token 数（那是**编造读数**，比不显示更糟）。

### 3.6 `ask`

权限门 / 提问。**core 会阻塞**直到 GUI 回 `answer`（一次只能有一个未决 `ask`，I3）。

```json
{"t":"ask","seq":29,"ts":"...","id":"q1","kind":"permission","question":"允许修改 docs/README.md 吗？","options":[{"key":"allow","label":"允许"},{"key":"deny","label":"拒绝"}],"default":"deny"}
```

> `default` 只在 GUI 侧超时/关闭时使用；正常路径必须显式回答。

### 3.7 `usage`

```json
{"t":"usage","seq":40,"ts":"...","turn":3,"input":18422,"output":913}
```

### 3.8 `error`

```json
{"t":"error","seq":41,"ts":"...","fatal":false,"message":"工具超时"}
```

### 3.9 `bye`

core 退出前的**最后一条**。

```json
{"t":"bye","seq":42,"ts":"...","reason":"eof","code":0}
```

| `reason` | 含义 |
|---|---|
| `eof` | stdin 关闭，正常收尾 |
| `cancel` | 被取消 |
| `error` | 异常退出，配合 `code` |

## 4. gui → core 消息

| `t` | 载荷 | 何时发 |
|---|---|---|
| `hello` | `protocol`、`gui` | 收到 core 的 `hello` 之后，`seq` 0 |
| `prompt` | `text` | 用户提交输入（仅 `idle` 时合法） |
| `cancel` | — | 用户点停止（`running` 时合法；`waiting` 时应改发 `answer`） |
| `answer` | `id`、`choice` | 回答一个未决 `ask` |
| `bye` | — | GUI 即将关闭，请 core 退出 |

```json
{"t":"hello","seq":0,"protocol":1,"gui":"0.0.1"}
{"t":"prompt","seq":1,"text":"帮我看看 README"}
{"t":"answer","seq":2,"id":"q1","choice":"allow"}
{"t":"cancel","seq":3}
{"t":"bye","seq":4}
```

**GUI 不产生转录块。** 用户输入由 core 回显为 `kind:"user"` 块——转录的**唯一作者是 core**（§8.3）。

## 5. 不变量

| # | 内容 | 违反时的可见症状 |
|---|---|---|
| **I1** | 一个 `id` 的 `block_start` / `block_end` **各恰好一次**，且 end 在 start 之后 | 卡片重复或永远转圈 |
| **I2** | 一个块的 `delta` 只能落在它的 start 与 end **之间** | 文本落到错误的卡片 |
| **I3** | 发出 `ask` 之后、收到 `answer` 之前，core **不得再发任何消息**（`usage` 除外）；`state=waiting` 是 `ask` 的**伴随消息**，必须紧随其后；**未决 `ask` 至多一个**。★ 夹具里 `answer` 是隐含的（§8.3）⇒ **可机检形式** = 「`ask` 后必须紧跟 `state=waiting`；在 `state` 回到 `running` 之前不得再发 `ask`」 | 权限门叠层 / 死锁 |
| **I4** | `seq` 每方向严格递增**且连续**；出现缺口 ⇒ **GUI 必须显式提示"消息丢失"**，不得静默继续 | 静默丢帧——本项目最想抓的失败 |
| **I5** | 未知 `t` / 未知字段被忽略并记录 | 崩溃 |
| **I6** | `block_end` 之后该块**只读** | 重放与实时两条路径行为不一致 |
| **I7** | `tool_result` 必须带 `for`，指向一个已存在的 `tool_call` id | 结果卡片挂不上调用卡片 |
| **I8** | 未知 `kind`（含**缺失** `kind`）必须**中性渲染 + 显式提示**：① 不得伪装成有语义的形态（工具卡 / 权限门）；② 正文**不得丢弃**；③ 必须计入读数。★ `reasoning` **不在**本条管辖内——它是 §3.3 的已知值，有专门的渲染形态（§7） | 思维链被当成「正在等的工具结果」，或未知内容被静默吞掉 |

> **I4 是本项目的核心评估钩子**：`Application::PostToUi` 的乱序/丢失只有靠它才看得见。

## 6. 状态机

```
        hello
          │
          ▼
       ┌──────┐  prompt   ┌─────────┐
       │ idle │──────────▶│ running │
       └──────┘           └────┬────┘
          ▲                    │  ▲
          │ block_end(all)     │  │ answer
          │                    ▼  │
          │              ┌──────────┐
          └──────────────│ waiting  │
                         └──────────┘
   running ──cancel──▶ cancelled ──▶ idle
   任意状态 ──fatal error──▶ error ──▶ 进程退出
```

GUI 侧对 `prompt` / `cancel` 的按钮使能**只由 `state` 驱动**（不要自己推测）。

★ **「使能」有两个断言，必须分别兑现**（2026-10-14 补）：
① **位**——按钮的 enabled 状态按上表翻转（`idle` ⇒ 发送可用 / `running`·`waiting` ⇒ 发送不可用）；
② **边界**——禁用后**点击不得到达**（不是「到了再忽略」）。

②**不能由 ① 推出**：两者是**独立的两段代码**（使能位是应用侧 `SetEnabled`，命中门控是
`Widget::HitTest` 的 `if (!IsEnabled()) return nullptr;`）⇒ 必须单独取证。
本仓库的取证方式 = `harness_gui --hit-probe`（在**同一点**上做 `as-is` / `off-point` /
`forced-enabled` / `forced-disabled` 四组受控对照，观测 `HitTest` 返回值 + 发送回调是否被进入；
**不注入系统输入**）。实测结论见 `docs/ecdi-capability-requests.md` 的 `REQ-04` 边界取证节。

★ 一条易混事实：控件禁用时 `HitTest` **不返回 `nullptr`**，而是**跳过该控件、回落到祖先**
（通常是 `RootWidget`，其命中区覆盖整个客户区）⇒ 「命中者不是该按钮」与「命中 `nullptr`」
是两种不同读数，别混为一谈。

## 7. 渲染映射（v1）

| `kind` | v1 渲染 | 用到的 ECDI 能力 |
|---|---|---|
| `user` | 右对齐、次要底色的一行文本 | `Label` / `Panel` |
| `assistant` | 纯文本，保留换行 | `Label` |
| `reasoning` | ★ **默认收起**的折叠块：标题 = `﹀ 思考中`（推理中）/ `﹀ 已完成`（已结束），带可选 token 副标；**点击标题展开，箭头翻转为 `︿`**（再点回到 `﹀`） | `CollapsiblePanel` + `Button`（与工具卡同机制） |
| `tool_call` | **可折叠卡片**，默认折叠；标题 = `name`，展开体 = `args` 美化 | `CollapsiblePanel` |
| `tool_result` | 可折叠卡片，标题 = `ok ? 成功 : 失败` + `summary` | `CollapsiblePanel` |
| `system` / `error` | 弱化色、居中 | `Label` |
| ★ **未知 `kind`**（含**缺失** `kind`） | **中性气泡**：琥珀描边 + 显式前缀 `[未知 kind: xxx]`，正文原样保留 | `Label` / `Panel` |

#### `reasoning` 的渲染形态（v2 新增，2026-10-14 用户定调）

**交互**：默认**不渲染正文**，只显示一行标题；标题可点，点开后箭头**从朝下变朝上**。

| 状态 | 箭头 | 标题文本 |
|---|---|---|
| 推理中（未 `block_end`） | `﹀` | `思考中` |
| 已结束（已 `block_end`） | `﹀` | **`已完成`** |
| 展开后（两种状态通用） | `︿` | 同左（文本不变，只翻箭头） |

★ **箭头字形（2026-10-14，用户指定）**：用户嫌 `▼`/`▲` **难看**，要求「类似于 `<` 尖括号
这种……**向下的尖括号和向上的尖括号**的样子，但是要**钝角**，大概 **120°** 的样子」，
随后**直接给出字形**：**`﹀`(U+FE40) / `︿`(U+FE3F)**。
实测（修正量具后，见下）：**134.5° / 135.7°**，细笔画，上下仅差 **1.2°**。

★★ **我此前两次把角度测反了，根因 = 量具公式符号错误**（记此以免重犯）：
- 首版公式写成 `acos((k²-1)/(k²+1))`，**正确应为 `acos((1-k²)/(1+k²))`**
  ⇒ 每个读数都被**镜像**为 `180° - 真值`。
- 后果一：我断言「`▼` 本来就是 118°、角度已达标，难看是因为实心」——**错**，
  它其实是 **62.0°（锐角）**。
- 后果二：我据此换上的 `∨`/`∧`，我说 127.7°/131.4°——**错**，其实是 **53.1°/49.1°（锐角）**。
  ⇒ 用户要的是**钝角**，我给的却是**锐角**，**方向完全反了**。
- ★★ **教训（本项目最该记的一条）**：**测量函数本身是仪器，未校准的仪器会给出自信的错数**。
  修正版**先喂解析式已知角度**的合成 V 形做校准（60/90/110/120/130/150，误差 ≤1.4°），
  通过后才测真实字形。**不校准就不报数。**（同族：条 76「量具不校准则判据无效」。）
- ★ 附带一条：多字节字面量**不得凭记忆手写**。我第一版把 `﹀` 的字节写成 `EF B8 80`
  （实为 `EF B9 80`，`EF B8 80` 是 U+FE00）⇒ 一律用 `chr(cp).encode('utf-8')` **程序化反查**。

★ **字形可用性是实测的，不是按名字猜的**（同一次取证）：`⌄`(U+2304) / `⯆`(U+2BC6) /
`〈`(U+2329) 等在当前字体**缺字**。★ 这条很关键：缺字会被 Windows **静默字体链接**到别的
face ⇒ 字重与基线与旁边文字对不上，**比原样更难看**。⇒ 选字形必须**实测存在性**。

★ **只有两态、一个标签位**（用户口径逐字：「默认应当不渲染，显示『思考中』这几个字，
加一个**向下的不带柄的箭头**，点击展开后箭头变为**朝上**的」）。
- **不带柄** ⇒ 不用 `⯆`/`⌄` 一类带柄字形；也不用工具卡那套 `▸`（那是**收起**态实心右三角）。
- 箭头**只由展开态决定**，与块是否结束无关。

★ **已结束为什么改文案（2026-10-14 用户裁决）**：用户答复「**块结束显示已完成**」。
理由与修掉 `等待结果` 占位标题同源——**流式态文案用在已结束的块上会失真**。
⇒ 文案随 `block_end` 从 `思考中` 变 `已完成`；**箭头不变**（仍是 `▼`，因为仍是收起态）。

★ **token 副标（v2 新增）**：`block_end.tokens` 存在时，标题追加 ` · N tokens`
（如 `▼ 已完成 · 1843 tokens`）；**不存在时不显示**，且**不得**用字符数冒充。

★ **收起 ≠ 不接收**：core 照常流式发完整思维链，GUI 全程接收并入账；收起只影响**渲染**。
★ **折叠态仍会测量**（A-2 结论）：收起时 `CollapsiblePanel` 的内容仍被布局测量一次
（ECDI 的 C29-10 缓存使其**不逐帧**重建）——这是**已知且有意的**，不是缺陷。

> ★ **实施期自伤（已撤回，记此以免重犯）**：我一度把「已结束」做成 **`▶ 思考过程`**
> （连**箭头**一起换掉），理由是"已结束还写思考中会失真"。
> **截图暴露代价**：绝大多数块都已结束 ⇒ 屏幕几乎全是 `▶`，而用户要的是**向下**箭头
> ⇒ **实际呈现违背了明确给出的规格**。用户随后裁决 = **只改文案、不改箭头**。
> ⇒ **纪律**：用户给了可见形态的具体规格时，**不要擅自替换**；有异议**提出来问**。


★ **未知 `kind` 的处置（2026-10-13 补，实测驱动）**：本节规则**仍然有效**——`reasoning`
成为一等公民**不会**取消它。§3.3 现在列七个值，而**其它**任何不在表里的值（`thinking` /
`analysis` / 拼错的名字 / **缺失字段**）依旧走这条中性路径。

⇒ 处置 = **中性渲染 + 显式提示 + 记账**（三者缺一不可）：
① 渲染不得**伪装成有语义的形态**（工具卡 / 权限门 / **`reasoning` 的折叠块**）；
② 正文**不得丢弃**（I5 的前向兼容精神是「忽略并记录」，不是「拒绝」）；
③ 计入摘要 `unknownKinds` 并在 GUI 协议健康里单列。
`validate.py` 对未知 / 缺失 `kind` 记 **note**（不判违规）。详见 `docs/ecdi-capability-requests.md` §2。

## 8. 回放（「假」的部分）

### 8.1 夹具是什么

**一份夹具 = 一段 core→gui 的消息流**（只有 core 侧，因为 GUI 侧的消息是对它的反应）。

### 8.2 两种回放模式

| 模式 | 行为 | 用来测 |
|---|---|---|
| `instant` | 一次性灌入全部行 | 稳态渲染 / 布局与滚动的极限 |
| `timed` | **按 `ts` 的真实间隔**逐条投递 | 流式刷新、重绘合并、帧时 |

`timed` 模式下，`ts` 的差值是**节奏的唯一真相源**——不要自己编延迟。

### 8.3 遇到 `ask` 时

`ask` 的正确回答**不可能存在于夹具里**（它是 GUI→core 的消息）。因此：

- `timed` 回放遇到 `ask` 时，把它**照常显示**并暂停在 `waiting`；
- 用户点选后，回放**继续**下一条 core 消息；
- 无人值守的自动跑批时用 `--auto-answer allow` 之类开关跳过等待。

★★ **回答的隐含边界（这条是 I3 能落成机检的前提）**：夹具里 core 的 `state` 由 `waiting` **回到 `running`**，
就代表它**已经收到了回答**。于是 I3 在夹具上不必检查不可见的 `answer`，只检查
「`ask` → 紧跟 `state=waiting` → 在 `state=running` 之前不得再发 `ask`」。

### 8.4 随附夹具

| 文件 | 用途 |
|---|---|
| `fixtures/demo-session.jsonl` | **正常路径**：完整一场会话（流式 / 工具成功 / 工具失败 / 权限门 / usage / 收尾），43 条消息，`seq` 连续无缺口 |
| `fixtures/hostile/seq-gap.jsonl` | **I4 的负向用例**：`seq` 缺口（3→5）+ 一个未知 `t`（`telemetry`）+ 一个指向不存在块的 `block_end` + 一条落在 `block_end` 之后的 `delta` |
| `fixtures/hostile/truncated-final-line.jsonl` | **§1.2 的负向用例**：最后一行被截断（半个 JSON） |
| `fixtures/scale/scale-transcript-2000.jsonl` | **规模基线**：2000 块 / 250 工具对 / 8906 条消息 / 916 KB，全部不变量成立。用于评估指标 ②（长转录滚动延迟与内存）；**建议 `instant` 回放**（`timed` 约 1.6 分钟） |
| `fixtures/scale/gen_scale.py` | **确定性生成器**：`--blocks N --seed S`，同参数必得**逐字节相同**输出 ⇒ 2000 / 5000 / 20000 是**旋钮**，不是砖 |
| `fixtures/cot/cot-session.jsonl` | **思维链基线**（开源推理模型）：12 轮，每轮一段**长、流式、本应折叠**的思维链 + 短回答。44 块 / 934 deltas / 1044 消息。★ 用 `kind:"reasoning"`（v2 一等公民）；`hello` 带 `context:128000`（百分比分母）；每个思维链 `block_end` 带 `tokens`（标题副标） |
| `fixtures/cot/gen_cot.py` | **确定性生成器**：`--turns N --thinking-chars C --kind reasoning\|unknown\|assistant --context N --tokens N`。用途：① `--thinking-chars` 做**长度剂量**（`measureChars/measureCalls` 随长度单调上升）② `--kind` 做**渲染形态对照**（收起 vs 可见）③ `--context 0` 做**分母缺失**降级路径（GUI 必须显示 `—`）④ `--tokens 0` 做**副标缺失**路径（不得用字符数冒充） |

**否定型断言必须配正对照**：先用 `demo-session.jsonl` 证明路径通，再用 hostile 目录证明失败被**显式**暴露。

### 8.5 可执行规格

`protocol/validate.py` 是 §5 不变量与 §1 编码约定的**可执行形式**——协议文档说「必须怎样」，它负责「真的拦得住」：

```
python protocol/validate.py            # 退出码 = 未通过预期的夹具数
```

| 目录 | 期望 |
|---|---|
| `fixtures/hostile/**` | **必须触发至少一条**不变量 |
| 其余全部 | **必须满足全部**不变量 |

★★ **hostile 夹具「什么都没触发」= 失败**，不是通过。理由与 ECDI 里那条一致：
**一个恒成立的负向用例，与没有这个用例无法区分**。

## 9. 版本与兼容

**当前版本 = `2`**。`hello.protocol` 是 core 声明的版本；本仓库 GUI 支持**上限 = 2**。

- `protocol` 是**主版本**。core 的 `protocol` > GUI 支持的上限 ⇒ **GUI 拒绝连接并显示原因**，不做降级猜测。
  ★ **`hello` 不携带 `protocol` 字段时按 v1 处理**（v1 时代该字段是必填，但宽容比拒连更安全——
  缺字段不是「更高的版本」，无法据此判定不兼容）。
- 同一主版本内：**只增不改不移除**字段；新增字段必须可被旧 GUI 忽略（I5）。
- 改任何已列出的字段语义 ⇒ 主版本 +1。

## 10. 这份协议服务于哪些评估

| 评估指标（对 ECDI） | 协议里对应的量具 |
|---|---|
| ① 流式 N token/s 下的重绘次数与帧时 | `delta` 的条数与 `ts` 间隔；GUI 侧统计每次 `delta` 引发的重绘 |
| ② 长转录的滚动延迟与内存 | `block_*` 的条数（夹具可放大到数千） |
| ③ `PostToUi` 突发下的顺序与丢失 | **`seq` 连续性（I4）** |
| ④ 跨 DPI 文本测量一致性 | 同一夹具在两个 DPI 下渲染，比对换行与滚动宽度 |
| ⑤ 做一个真实 GUI 花了多少行 / 多久 | 本协议的实现规模本身就是这个数字 |

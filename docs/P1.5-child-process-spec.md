# ECDI_fake_harness · P1.5 实施规格：子进程真路径（假 core ↔ 真管道）

> **定位**：P1 的 GUI 是「协议的渲染器」，只吃夹具（core 侧单向录制）。
> P1.5 = 把同一份协议接上**真双向通道**——子进程、管道、线程边界全部走真的。
> 轻量实施规格，不启用 ECDI 三件套。
> 状态：**v1.2 已实施并收口**（2026-10-08；v1.2 = 实施回写，见 §8）。
> ★ 用户定案（2026-10-07）：**UI 线程模型 = 先阻塞读**（保持 P1 回放模型的形状，读数可直接对比）；
>   async 投递（PostToUi）留作 **P2 对照实验**——那正是协议指标③想要的场景。
>   ⚠ **实施期该定案被修正**：无限阻塞读会让 UI 线程卡死消息循环（实测窗口全黑，`.scratch/p15-live-1.png`），
>   改为 **UI 线程按 8ms 预算轮询 `NextWithin`**（见 §4.2 / §8 R-1）。`PostToUi` 至今**零消费**（§8 R-2）。

## §4 接口定义

### 4.1 MessageSource 扩展（源能力可选化）

现状 `Next(line)` 对回放/子进程都够用，但 UI 还需要「进度/总量」与「写通道」。
**不改 `MessageSource` 基类**（避免子进程被迫实现回放语义），改为：

```cpp
// MessageSource.h 追加（不破坏既有实现）
class MessageSource {
public:
    virtual ~MessageSource() = default;
    virtual bool Next(std::string& line) = 0;      // 阻塞读一行；EOF/致命错误 false
    virtual bool IsLive() const { return false; }  // 回放=false，子进程=true（UI 措辞/进度条用）
    virtual bool Send(const std::string& line) { return false; }  // 反向通道；不支持=false
};
```

`ReplaySource`：只 `override IsLive() → false`，其余零改动（`Next/NextDue/Total/Consumed` 保持具体 API）。
`ChildSource`：`Next` 从内部队列阻塞取行；`Send` 写子进程 stdin；`IsLive() → true`。

**App 侧改造**：`ReplaySource m_source` → `std::unique_ptr<MessageSource> m_source` +
`ReplaySource* m_replay = nullptr;`（仅当回放时非空，供进度条/Total 用）。
所有 `m_source->Total()` 读数改为「有 `m_replay` 取具体值，live 模式显示已收条数」。

### 4.2 ChildSource

```cpp
class ChildSource : public MessageSource {
public:
    ChildSource();
    ~ChildSource() override;

    // 启动子进程；false + error = 失败（命令行无法解析 / CreateProcess 失败 / 管道创建失败）
    bool Start(const std::filesystem::path& exePath,
               const std::string& args, std::string& error);

    // MessageSource
    bool Next(std::string& line) override;   // 阻塞：队列空则等；EOF 且队列空 → false
    bool Send(const std::string& line) override;  // 追加 '\n' 写 stdin；进程已退 → false
    bool IsLive() const override { return true; }

    // 关闭：关 stdin（让 core 走 eof 收尾）→ 等宽限期 → 必要时 TerminateProcess
    void Stop(int graceMs = 1500);

    // 诊断
    size_t LinesReceived() const;   // 已收到行数（live 模式的"进度"）
    bool Exited() const;
    int ExitCode() const;
};
```

**线程模型（关键）**：
- `ChildSource` 内部起**一个**读线程：`ReadFile(stdout)` → 按 `\n` 分行 → 加锁入队 → 有界上限（8192 行）防失控内存；
- ★ **UI 线程走 `NextWithin(line, budgetMs)` 轮询**（`App.cpp:628`）：每 tick 先给 `budgetMs = 8` 等第一行，
  同 tick 内再以 `timeoutMs = 0` 非阻塞取空队列，然后把时间还给消息循环；
- ★ **无限阻塞的 `Next` 不得由 UI 线程调用**——`ChildSource.h:36` 已显式注明「会卡死消息循环」。
  实测依据：阻塞读 ⇒ `WM_PAINT` 饿死、**窗口全黑**（`.scratch/p15-live-1.png`）；改轮询后正常（`.scratch/p15-live-2.png`）。
  ⇒ **原定案「UI 线程阻塞读」已废弃**（见 §8 R-1）；`Next` 仅供离线 / 测试路径使用。
- `Send` 由 UI 线程调用，直接 `WriteFile(stdin)` + `FlushFileBuffers`；加写锁（读线程不写，故只需防未来多写者）。

### 4.3 PostToUi 的角色（★ 实施后：仍为零消费）

原计划（v1.1）让 `PostToUi` 承担「`Stop()` 前的 stdin 写入 + 等待」，避免退出路径跨线程写管道。
**实施期未落地**——`grep PostToUi gui/src/` 全库唯一命中是 `App.cpp:624` 的**注释**（「P2 改用 PostToUi 异步投递」）；
`ChildSource::Stop()` 直接在调用线程关句柄 + 宽限等待，**不经** `PostToUi`。

- `ChildSource` 读线程**不直接** `PostToUi`：保留「读线程 → 有界队列」为唯一真相源（这一点按原计划执行）；
- **`--core-async` 开关未新增**（原规格已判「不做」，实施一致）。

★ **实施定案**：`PostToUi` 在本阶段**零消费** ⇒「ic 首次使用 ECDI 的跨线程能力」**未兑现**，
首次真实消费顺延到 **P2**（届时用同一假 core 做「轮询 vs 异步投递」对照，正是指标①/③要的读数）。

> **登记待决（P2）**：UI 线程轮询（现状） vs PostToUi 异步投递——两条路的读数差异正是指标①/③想要的，P2 立项时同一假 core 对照。

### 4.4 反向通道（ProtocolWriter）

```cpp
class ProtocolWriter {
public:
    explicit ProtocolWriter(MessageSource& sink);
    bool Hello(const std::string& guiVersion);          // seq 0
    bool Prompt(const std::string& text);               // 仅 idle（调用方保证）

    bool Bye();
    long long LastSeqSent() const;

    MessageSource& m_sink;

```
序列化：`json::Value` → `Dump()`（§3 补的公开 API），字段序 = `t, seq, ts`（与 core 侧一致；`ts` gui→core 可省，协议 §2 标「core→gui 必填」）。

## §5 假 core 行为（`core/script.go`）

收到 `prompt` 后的脚本（确定性，`--seed` 固定）：

1. `state=running`；
2. **回显用户**：`block_start kind=user`（转录唯一作者是 core——协议 §4）；
3. **助手模板流**：3–8 段 Markdown 文本（**复用 `protocol/fixtures/realistic/gen_realistic.py` 的语料**，避免第二份真相），每段切 4–12 个 `delta`，间隔 30–300ms（`--fixture-speed` 缩放）；
4. **工具对**：1–3 次 `tool_call` + `tool_result`（结果 = 预置日志文本，4–40 行）；每 N 次插一个 `ask`：
   `ask` → `state=waiting` → **阻塞等 stdin 的 `answer`**（I3 自守：期间不发任何消息）；
5. `usage` + `state=idle`。

**`--drop-seq`**：每 K 条消息跳一个 seq 号（**错误地**递增 2），用于验证 harness 的 I4 提示真的响。
**`--drop-block-end`**：跳过一个 `block_end`（I1 负向）。
**`cancel`**：收到后立即 `state=cancelled` → `state=idle`，丢弃进行中的剩余 delta。
**`bye` / stdin EOF**：`bye` 收尾后退出 0。

## §7 已知局限（明确推后）

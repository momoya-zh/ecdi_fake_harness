# 定位与信任模型

> 本文件回答三个会被反复问到、且**答错就会把项目做偏**的问题：
> ① 这个仓库到底为什么存在？② 「能用」和「评估」冲突吗？③ 让真 agent 干活，风险怎么控？
>
> ★ 建立缘由（2026-10-14，用户定调）：我曾把本项目理解为「纯评估夹具」，并据此推出
> 「可以让真 agent 的工具永不真正执行，而评估保真度不损失」。**该结论被用户否决**，
> 理由见 §2。**原判以引用形式保留在 §2.3**（条 30 / 61②：历史不改写）。

---

## 1. 两个目的，以及它们为什么不冲突

| # | 目的 | 判定它成功的标准 |
|---|---|---|
| **①** | **对 ECDI 的评估数据 + 能力需求账本** | `evals/` 的读数、`docs/ecdi-capability-requests.md` 的条目 |
| **②** | **一个真正能用的 agent GUI** | 接上真 agent 后，**人能拿它干活** |

★ **两个目的都是第一等的**。目的 ② 不是目的 ① 的副产品——**它本身就是交付物**。

### 1.1 为什么这不需要分叉成两个项目

`MessageSource` 这个接口（`gui/src/MessageSource.h`）已经把两条路分开，而 GUI **同一份**：

| 实现 | 角色 | 特性 |
|---|---|---|
| `ReplaySource`（夹具回放） | **确定性仪器** | 逐字节可复现、可做受控对照、可进回归基线 |
| `ChildSource`（真子进程） | **可用工具** | 真时序、真负载、真失败模式；**不可复现** |

⇒ **一个代码库，两个来源，两套用途。** 这不是折中，是**接口本来就该长这样**：
GUI 只依赖「core→gui 一行消息的来源」，不关心背后是文件还是进程。

### 1.2 但两条路的读数**不得混入同一份基线**

`ReplaySource` 的读数（如 `demo 8/19/43`）是**契约**——变了就是回归。
`ChildSource` 的读数**天然浮动**（网络、模型、调度）。

★ 把它们放进同一份「基线」= 把「今天网络慢」记成「ECDI 有缺陷」。
这正是本项目前 4 次归属反转的**同一类陷阱**：拿不可控的输入去下因果结论。

## 2. 可用性为什么是评估可信的前提

### 2.1 展示品碰不到真问题

一个**不能真干活**的 harness，永远撞不上那些真正要命的失败模式：

- 真实突发下的 `PostToUi` 乱序/丢失（`REQ-03`，协议指标 ③ 的唯一钩子）
- 真实长会话的内存与滚动退化
- 真 agent 的失败/重试/重连路径
- 8ms 轮询预算在真实负载下够不够（`docs/P1.5-child-process-spec.md` §7 已登记为待验）

⇒ **只测得了假 core 能造的负载，就只发现得了假 core 能造的问题。**
把仪器调钝，然后宣称读数依然有效——**那是自欺**。

### 2.2 独立仓库本身也要求它「能用」

如果本项目只是**展示**，它就该待在 ECDI 的 `examples/` 里，不该单独占一个仓库。
⇒ **单独成仓 = 它必须提供 `examples/` 提供不了的东西**，也就是「真能拿来用」。

### 2.3 ★ 我的原判（已作废，保留链条）

> 原判：「我们评估的是**渲染**，不是**能力**。一个 `tool_call` 块——`name:"bash"`、
> `args:{...}`——**执行与不执行，GUI 渲染出来一模一样** ⇒ 可以让真 agent 的工具
> 永远不真的执行，而评估保真度一点不损失。」
>
> ★ **作废理由**：该推论**在"渲染保真"这一维度内成立**，但它把项目**降格成了展示品**。
> 它犯的错是**把「不该让 agent 乱来」误推成「不该让 agent 干活」**——这是两件事：
> 前者是**隔离问题**（§4.3），后者是**可用性问题**（本节）。
> 用前者的顾虑去砍掉后者，等于用安全当借口砍掉项目的存在理由。

## 3. 为什么必须是独立仓库（两个**独立**理由）

★ 这两条**各自都成立**，不是一条的两个说法：

| # | 理由 | 依据 |
|---|---|---|
| **① 外部性** | 评估者必须是**外部消费者**。ECDI `examples/` 里的东西是 ECDI 的一部分，不可能当客观消费者 | 铁律：本仓库**不改 ECDI**，只登记需求 / 给证据 / 判归属 |
| **② 可用性** | 一个能真用的 agent GUI，其体量与演进节奏都超出 `examples/` 的定位 | §2.2 |

⇒ 即使有一天「外部性」不再是问题（例如有了别的消费者），**②** 仍然成立。

## 4. 信任模型

### 4.1 协议**不是**安全边界

`PROTOCOL.md` 是**渲染契约**：它规定「core 发什么、GUI 怎么画」，**不规定 core 能做什么**。

★ 这一条有外部佐证：[MCP 的安全文档](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)
对 stdio 传输写得很直白——

> "the client and a stdio server **share one trust domain** … there is **no boundary between
> the two processes** for a transport to enforce"
>
> "**The stdio transport is not a sandbox.**"
>
> "Your real security decisions happen **before launch**: what you install (provenance)
> and how you run it (isolation)."

⇒ 我们的 stdio 通道（`gui/src/ChildSource.cpp`，`CreateProcessW` + 双向管道）**同理**。
它传消息，不提供隔离。

### 4.2 `ask` 权限门是「**用户在环控制**」，不是安全机制

协议 §3.6 写「core 会阻塞直到 GUI 回 `answer`」。★ **这是合作性契约**：

- **能检测**：I3 让「没阻塞就继续发消息」在**消息序**上看得出来（§5 的可机检形式）
- **拦不住**：一个想跑 `rm -rf` 的真 core **不必先问我们**

⇒ 想把它当安全边界用是**用错工具**。但它在**另一个用途上是必要且有效的**：

> **让用户看清一个「可信但会犯错」的 agent 打算干什么。**

后者正是**可用 harness 的核心功能**（§1 目的 ②）。⇒ 它的定位是**人在环控制**，
不是防线；**两者都要写清楚，否则读协议的人会以为拿到了它没提供的保证**。

### 4.3 真执行 ⇒ **必须** OS 级隔离

一旦 launch 真 agent 并允许它执行工具，**隔离就不是可选项**：

| 层 | 谁负责 | 管什么 |
|---|---|---|
| 协议 | 本项目 | **只**管渲染语义（不提供任何隔离） |
| `ask` 门 | 本项目 | **用户知情与同意**（合作性） |
| **进程/OS 隔离** | **运行者** | 它**乱来的时候能做什么** |

⇒ 容器 / VM / 受限账户，**由运行者保证**。本文档把它写成**前置条件**，不是建议。

★ **诚实标注**：本仓库**不实现**隔离，也**不检查**它是否存在。
一个没做隔离就跑真 agent 的用户，拿到的是一个**没有护栏**的工具。
把这句话写在这里，比让它隐含在代码里更负责。

## 5. MCP 的位置（决策：**A — harness 管理 MCP 配置**）

### 5.1 两条边，不同层

```
        ┌─────────────┐
        │  真 agent   │
        └──┬───────┬──┘
    MCP  │       │  我们的协议 v2（JSONL / stdio）
(JSON-RPC)│       │
        ▼       ▼
   工具 / MCP   harness_gui
    servers     （渲染 + 权限门 + **配置管理**）
```

- **MCP**：agent ↔ 工具（server 提供 tools / resources / prompts；client 提供 elicitation 等）
- **我们的协议**：agent ↔ GUI

⇒ **我们不是 MCP server**（不提供工具）。是否当 **MCP host**（管配置、拉起 server）——
这是本节要拍的决策。

### 5.2 决策 **A**（2026-10-14 用户拍板）：harness 管理 MCP 配置

**理由**：给完整的工具链，后面要。一个真能用的 agent GUI，用户预期它管这件事。

**代价（必须一并接受，不能只拿好处）**：
MCP 的 **host 是「授予能力」的一方**。当了 host，**爆炸半径就是我们的责任**——

- 我们负责**拉起** MCP server 进程
- 我们负责**展示**将要执行的调用（`tool_call` / `ask` 门）
- 我们**不**负责（也无法）在协议层拦住它 ⇒ 见 §4.3，隔离是运行者的责任

★ 配套纪律：**harness 只做「配置 + 展示 + 转发」，不做「策略」**。
任何「这个工具该不该允许」的判断归**用户**（经 `ask` 门），不归 harness 的启发式。
一旦 harness 开始替用户判断，它就在做一个它没有能力做对的**安全决策**。

### 5.3 MCP 侧的时效性事实（2026-07-28 版规范，**已核**）

★ 记下来是因为 MCP 演进快，凭记忆会写错：

- 基础协议 = **JSON-RPC**，**无状态、自包含请求**，**逐请求能力协商**（不再是连接级 `initialize` 会话）
- 传输 = **stdio**（换行分隔）· **Streamable HTTP**（单端点 POST + 可选 SSE）
- ★ **Roots 与 Sampling 已废弃**（deprecated as of `2026-07-28`）——若将来引用它们，那是旧版语义
- 扩展（**opt-in**，初始化时协商）：**Tasks**（长任务：轮询 / 中途输入 / 持久句柄）等

⇒ 实现 MCP host 时，**以规范日期为锚**（`2026-07-28`），不要照抄博客/旧 SDK 示例。

### 5.4 渲染侧已经就位

MCP 的工具调用落到我们的协议上**不需要新块类型**：`tool_call` / `tool_result` 已经覆盖
（`PROTOCOL.md` §3.3 / §3.5，含 `args` / `summary` / `ok`）。
⇒ **MCP 接入主要改的是配置与生命周期，不是渲染。**

> **本仓库是一个「外部消费者」造的、能真用的 agent GUI；它顺手产出对 ECDI 的评估数据。
